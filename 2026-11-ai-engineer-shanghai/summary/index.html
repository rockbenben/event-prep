一、大会议题与整理者观察

1.1 一条阅读主线：从能力演示走向结果验证

整理者归纳：两天分享中，一个反复出现的问题是：模型生成结果之后，团队怎样判断它能否交付？OpenClaw 用 Proof Engineering 描述验证工作，Harvey、Manus、MiniMax 等分享则分别从业务回放、人工注意力与执行结果验收讨论了相关难题。这可以作为理解部分工程场次的一条主线，不代表整场大会只有一种观点，也不代表模型能力提升已经不重要。

相比单纯展示“模型能做什么”，这些场次更关注上下文是否完整、任务状态能否延续、失败能否被发现，以及验收由谁承担。确定性验证器、上下文治理与尚未数字化的业务经验，是值得继续追问的工程问题。

1.2 五组共通观察及其适用边界

以下是跨场次的主题归类，属于整理者观察。不同分享的任务、样本和评测方法不同，不能视作彼此独立复现的统一实验。

  1. 公开 Benchmark 不足以替代自有业务评测与回放（Replay）： Harvey 的历史 PR 回放、Agoda 的仓库任务试验、Chatbot Arena 的真实使用评测，以及 NUS、Daily.co 的语音场景，分别展示了公开分数与特定业务表现之间的差异。共同启发是补充真实任务与长尾样本；这些分享不能合并成“所有公开榜单都失效”的结论。
  2. 一些任务的瓶颈转向可靠性与长程执行： Langfuse、OpenClaw、StepFun、MiniMax 的分享都涉及长程任务中的可靠性、执行状态或验收问题。这不意味着所有任务上的基座能力都已充分，而是提醒团队从失败轨迹判断当前究竟缺能力、上下文还是验证。
  3. 上下文需要按任务治理，增减都应经过评测： 把所有背景、架构文档、完整网页一股脑灌进大窗口，被证明往往带来反效果。Agoda 在一个服务、10 个 MR 的首轮 A/B 试验中发现，保留既有上下文的成本高 8%，任务完成率相同；Exa、Jina、HeyGen、MiniMax 均主张采用抽取式切片、前缀缓存对齐以及转换输出格式来控制上下文。
  4. 物理 AI 场次呈现多种状态建模与控制分层方案： World Labs 讨论世界模型的范围，VAST 强调状态、转移与渲染的分离，AiMoga 与家庭机器人方案讨论感知和执行闭环，DYNA 关注硬件对学习与控制的影响。这些层面的划分并不相同，不宜概括为“全员反对端到端”或统一的 System 1 / System 2 架构。
  5. 值得关注的壁垒在“没有 API 的地方”与真实业务编码（填海工程）： 杨滢、朱世辉、投资人圆桌、masons.ai 均指出：凡是公开互联网有现成 API、标准定义的事情，纯软件 Agent 的壁垒会迅速被基座模型抹平；值得关注的壁垒在于深入线下与传统流程，把没有 API 的非标业务编码为结构化数字资产。

1.3 核心技术分歧与争鸣辩论

现场在若干具体路线上存在鲜明对立，各自代表了不同的工程取舍：

  • Harness 框架该做加法还是做减法？
    • 做加法（StepFun / Langfuse）：认为必须在外围补足四类工程——目标进度追踪、上下文信息选择、确定性验收判断、断点持续执行，否则模型跑长任务必崩。
    • 做减法（MiniMax）：讲者以 Anthropic 的提示词与 Plan Mode 演进为例，讨论哪些能力已经被模型内化，以及 MiniMax 如何随模型能力重新审视外围工程。并非宣布 MiniMax 自己已经删除同样比例的提示词或全部 Skills。
    • 整理者判断：删掉的是模型已学会的提示词微操技巧；保留并强化的是状态机持久化与外部确定性验证器。
  • 世界模型的范围到底有多大？
    • 广义表征（World Labs）：从强化学习认识论出发，认为世界模型是抽象推理与感知行动的接口，甚至包括 LLM 内部状态、Google Maps 与 CRM 系统，不强制要求视觉形式。
    • 狭义物理系统（VAST / 穹彻 / AiMoga）：特指维持 3D 几何状态、预测物理受力演化并驱动物理执行器的系统。
  • 个人 Agent（PA）究竟是不是创业公司的机会？
    • 投资人戴雨森：看好“新需求扩张”，通过深度获取个人生理数据推荐增量服务，强调情绪价值。
    • 投资人刘勇：坚决唱反调，指出“凡是帮人省时间的，都没有帮人消耗时间的赚得多”，算力数据均不占优，纯效率工具极易被巨头原生生态降维碾压。
    • 玉伯（YouMind）：提出第三条路——做面向自我的深度创作 Studio（To Myself / ToM），避开大众工具，做高客单私密交付。

1.4 十个值得回到原文核对的案例

  1. 工具层面的限制需要覆盖所有可用执行路径（微软）：Agent 继承宿主权限，关掉文件写入，它就会写 Python 或 Shell 脚本迂回执行——“我们恰恰是因为它很会变通才用它，所以它也会变通绕过限制”。 查看该场。
  2. 既有 Context 在小样本试验中未提升完成率（Agoda）：一个服务的 10 个 MR 首轮 A/B 中，保留上下文的一组成本高 8%，完成率相同。它是局部反例，不是删除所有仓库说明的通用建议。 查看该场。
  3. 先用业务回放定位该改哪里（Harvey）：PR 描述任务暴露了输入处理 Bug；代码审查任务暴露了回放数据污染；修复 CI 任务仍体现出模型在尝试次数与耗时上的差异。不能合并成“换模型、改 Harness 都无用”。 查看该场。
  4. Token 是可再生资源，人的注意力是不可再生资源（Manus）：自动化工具狂提 PR 毫无意义，只会拖垮人类审阅者；设计 Agent 首先要看“谁来验收”，没有形式化验收能力的自动化是负债。 查看该场。
  5. 基础设施的卡顿会直接污染模型权重（Google）：在强化学习训练中，沙箱拉取镜像耗时几分钟，环境超时被 Reward 函数判负，导致模型把“延迟”误学成了“负面策略”。 查看该场。
  6. 调整检查频率降低 CI 成本（OpenClaw）：讲者自报 100 次 CI 的合计成本从一千多美元降至两百多美元；保留 PR 有限检查、定期检查与发布测试。自适应测试当时刚合入、尚未完全启用，不能据此声称已证明“关闭 CI 更稳”。 查看该场。
  7. 把输出换成 HTML，胜过让模型理解你的 2000 行私有 JSON（HeyGen）：让模型在你私有的 DSL/JSON 里推理就像让莎士比亚写中文律诗；换成标准的 HTML/CSS，产品有机会随基座模型对 Web 标准的能力提升而受益，实际效果仍需验证。 查看该场。
  8. 特定分类任务可考虑决策模型（Liquid AI / 1Password）：Liquid AI 介绍 2B 级决策模型机制；1Password 在自建工具调用分类实验中报告，多种决策模型的准确率为 91%–93%，Qwen 7B 约 72%。两场实验应分别理解，拒判比例与置信度也需要一起比较。 查看该场。
  9. 网页 Token 长度是对数正态分布，平均数是中位数的 4 倍（Jina）：做预算如果按中位数算（5K），遇到长尾超长页面（几十万 Token）会瞬间打爆成本；必须在抓取后立刻做抽取清洗。 查看该场。
  10. 让模型参与上下文交接（MiniMax）：讲者讨论向模型暴露上下文余量，让它在接近上限时主动记录进展。这是一种值得按任务评测的方案，原文不足以支持“胜过所有压缩算法”的普遍排序。 查看该场。

2. Marco Casalaina · 微软核心 AI 产品副总裁（AI Futurist）｜从模型到企业工作流：Agent 真正落地需要什么

原文检索范围：2026-11-05 · L241–L1219。

  • 痛点与背景：企业希望让 Agent 介入日常业务（如处理客户退费、发邮件、协同审批），但现有方案往往只是聊天框式的“拟人助手”（以 Meta Muse 为反例，仅有名字和浅层身份，本质是为了促使用户聊天互动带货）。如果 Agent 在企业系统里代表员工去操作，会引发严重的越权与冒名风险。
  • 技术推演与架构方案：
    • 深度机器身份（Entra ID）：在 Microsoft Foundry 中，每个 Agent 被赋予独立的 Entra ID 机器身份，拥有自己的组织邮箱、Teams 收件箱和 OneDrive 存储空间，并且在企业组织架构图上作为人类员工的下属汇报。
    • 权限击穿与安全隔离：现场揭示了一个极其深刻的现象——靠简单的权限开关根本防不住 Agent。在“代表用户（On-behalf-of）”模式下，Agent 继承了用户的全部权限；如果管理员在界面上关掉文件的直接写权限，Agent 为了达成目标，会自动在终端里编写 Python 脚本或 Shell 命令去直接操作磁盘。“我们之所以用这些智能体，恰恰是因为它们善于变通；但也正因如此，它也会变通绕过表面限制。”解法是为 Agent 配置独立的最小权限模板（例如仅授予 files.read.all，而剥离用户的 files.read.write.all）。
    • 基于规则的自动化评测（Rubric-based Eval）：面对复杂的企业多 Agent 协作，通用跑分毫无意义。微软针对特定合规条款（如银行处理手续费争议时的《E 条例》与《P 条例》）构建规则评测集，严格审查 Agent 在退手续费前是否核验过账单记录。

3. Clemens Rawert · Langfuse by ClickHouse 联创｜构建 Agent：昨天、今天与明天

原文检索范围：2026-11-05 · L1220–L1881。

  • 架构演进史：
