# 写作细则：每一节怎么写才对

SKILL.md 规定了**产出什么**，这一份规定**怎么写**。写 `event.md` 之前过一遍。

---

## 页面上的展开规则：什么收起来，什么摊着

页面的读者是**站在会场门口用手机的人**。所以：需要时才展开的内容，收成点开式；
扫一眼就要用的，摊着。

| 章节 | 页面上的样子 | 为什么 |
| --- | --- | --- |
| 最重要的 3 件事 | **摊开**，在页面最上面的醒目框里 | 全篇最该被看到的东西，藏起来等于没有 |
| 速览 | **摊开** | 扫一眼就要用的，展开才扫得到 |
| 推荐路线 | **摊开** | 决策内容，是这一页的产出 |
| 日程 | **按天折叠**，第一天默认展开；一场一张卡片，占满整行 | 本来就长，收起才看得完；并排会挤 |
| 机构与嘉宾的备注 | **在日程里那一场的讲者行就地标注**（第 4 段） | 读者扫日程时一眼获取背景，无需跳到页尾翻找 |
| 机构与嘉宾的长介绍 | **写在讲者行第 5 段**，渲染成讲者名后的小图标 | 就地取用，不用翻到页尾；只在那个人第一次出现处挂 |
| 看这场之前要懂的术语 | **写进那一场的 `- 备注:`**，渲染成小图标 | 术语要挂在用得上的那一场上，不是另开一节 |
| 行前清单 | **摊开** | 要能直接勾，折叠了就没法用 |
| 社交与提问 | **摊开** | 通常 1–3 行，折叠反而多点一次 |
| 信息来源与待确认 | **摊开** | 每条只有一行，展开也不长；而且它是可信度的凭据，藏起来等于毁掉它的作用 |
| 活动页头部基本信息 | **手机上收成一行**，点开看全部；桌面摊开 | 手机上这五行会占掉大半屏 |

**没有「机构与嘉宾」「前置知识」这两节了**——它们的内容都变成日程里的图标提示。
**别的章节的三级标题照常是普通小标题**——不要在「速览」里用 `###`，那节本来就是扫的。

---

## 最重要的 3 件事

它是正文第一段的引用块：

```markdown
> **最重要的 3 件事**：主论坛是英文、设有同声传译，请提前在官网选好语言通道；
> Day 2 的「Agent 工程」分会场需要单独报名，名额有限；展区 Demo 需现场扫码预约。
```

构建器会把它提到正文最前面的一个醒目框里，**正文里那个「最重要的 3 件事」标签会被自动去掉**（模板已经给这块起了标题）。所以你照常写标签就行，不用担心重复。

**一行一件事**：引用块里的换行在页面上就是换行（构建时按硬换行处理），三件事写三行。全挤在一行的话，那块最该被扫到的东西会变成一坨连续文字。

**写什么**：时限性 → 决策性 → 易错性，各取先到先得的，最多 3 条。

**不写什么**：
- ❌「本次大会有众多精彩议题」——没有信息量。
- ❌ 把整个「速览」塞进来——那是下面章节的活。
- ❌ 为了凑 3 条把不痛不痒的写上。

## 速览

读者 30 秒内要判断「这活动值不值得去」。

**该有**：主办方、规模、票务状态、语言 / 同传、形式（一天还是两天）。
**不该有**：大段的宣传语、形容词堆砌。

```markdown
## 速览

- 主办方：AI Engineer
- 规模：两天，主论坛 1 个 + 分论坛 4 个，约 60 场分享
- 语言：英文为主；中文同传在 A 馆提供
- 票务：官网早鸟票已停售，标准票在售
```

## 场地：名字要能点

写在 front matter 里，不在正文里：

```yaml
city: 上海
venue: 上海虹桥希尔顿酒店（Hilton Shanghai Hongqiao）
venue_url: https://www.hilton.com/en/hotels/shashhi-hilton-shanghai-hongqiao/
address: 上海市闵行区红松东路 1116 号
map_url: https://www.google.com/maps/search/?api=1&query=上海虹桥希尔顿酒店+红松东路1116号
```

- **`venue` 用官方名字**，中英文都带上——读者可能是照着屏幕上的名字找过去的。
- **`venue_url` 是场地的官方页面**（酒店官网、场馆官网）。写了它，页面上的场地名会变成链接，
  头部还会多一个「场地」按钮。手机上头部信息是收起来的，那个按钮是唯一的入口。
- **`address` 写街道地址**，不要只写「上海」。外地读者靠它打车。
- ⚠️ **同名的场所有好几家时，地图的搜索词会落到别的那家去**
  （「上海虹桥希尔顿」和「上海虹桥国际机场希尔顿」是两家不同的酒店）。
  地图查询词带上地址，别只写酒店名。
- 找不到官方页面就**别写 `venue_url`**，写一个编造的地址比不写更糟。

## 推荐路线

**这是全篇最有价值的一节**——它把「日程」变成「决策建议」。

**角色已知**：

```markdown
## 推荐路线

**如果你在做基建 / 推理侧**：优先 Day 1 上午的推理成本专场，
Day 2 上午的 KV-Cache 与缓存分层专场。

**如果你在做应用侧**：Day 1 下午的 Agent 工程专场、Day 2 下午的评测与可观测专场。

⚠️ 两场都排在 14:00–15:00，属于并行场次，只能选一个。
```

**角色未知**：按这个活动适用的两类典型角色各给一套（而不是随便编两种角色）。

**每条建议必须能落到具体场次**。❌「推荐关注 AI 相关话题」 ✅「优先 Day 1 上午的推理成本专场」。

**并行冲突要点名**——这是读者最需要的信息之一。

## 日程

**不是表格**：一天一个 `###`，一场一个 `#### 时间 · 标题`，下面跟字段列表。
构建器把这一整节接管，渲染成一套自适应卡片——窄屏单列、宽屏同时段并排，
不用横着滚。

```markdown
## 日程

### Day 1 · 11 月 5 日（周四）主题一句话

#### 09:30–09:45 · 开场与年度趋势
- 形式: 开场
- 会场: 主会场
- 讲者: 主办方团队 | AI Engineer

#### 14:00–15:00 · Agent 工程化
- 形式: 演讲
- 会场: C 馆分会场
- 讲者: 张某某 | 某某科技 | assets/speakers/zhang.webp | 基础设施负责人
- 时长: 60 分钟
- 看点: 工具调用失败之后的重试与幂等，是生产 Agent 最容易出事的一段。
- 摘要: 把一次调用的成本拆成算力、缓存与网络三段，逐段给可核实的数字。
- 出处: https://example.org/program
```

### 字段

**字段是封闭集合**——名字拼错构建就报错，并给出 `event.md` 里的行号：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `形式` | 是 | `演讲` `圆桌` `快闪` `开场` `闭幕` `茶歇` `边会` `行程` `签到` 之一 |
| `会场` | 是（`签到` 除外） | 自由文本。同一时段的不同会场就是并行轨道。`签到` 发生在入口，不在会场里，所以不写 |
| `讲者` | 否 | 一行一人，最多五段：`姓名 \| 机构 \| 头像 \| 一句话注记 \| 完整介绍`，后四段可省 |
| `时长` | 否 | 如 `25 分钟` |
| `状态` | 否 | 还没定下来的事（见下） |
| `看点` | 否 | 我们写的一句话判断，帮读者 30 秒决定听不听 |
| `摘要` | 否 | 这一场的中文摘要 |
| `备注` | 否 | 看这一场之前要知道的事（术语、注意事项），可写多条 |
| `出处` | 否 | 该场的官方链接（页面上是一个小图标，指向中文版） |

**讲者行的五段是固定的**：`姓名 | 机构 | 头像 | 注记 | 完整介绍`。
第三段是**头像位**，写 `assets/speakers/<slug>.webp`；第五段是**完整介绍**，
渲染成讲者名后面那个小图标（点开是全文，只在那个人第一次出现的地方挂一个）。

没有头像时第三段留空；没有注记时第四段留空：

```markdown
- 讲者: 张三 | 某某科技 | | | 某某科技的资深工程师，做过推理引擎。
```

**一场里有几个人，就写几行 `讲者`，每人都写全五段。**
不要把几个人的介绍拼在一个人身上——页面上那个图标会挂在错的人旁边，
其余几个人既没有头像也没有介绍。
圆桌、对谈这类场次尤其容易犯这个毛病：**官方议程页上那一场的讲者常常是空的**
（头像要从官方**讲者页**抓），所以写之前先按讲者页把名单对一遍。

⚠️ **位置不能错**：把简介写到第三段（四段式）会被当成头像路径，构建报错说
「头像「某某科技的资深工程师…」要写成 assets/ 下的站内相对路径」。
第三段要么空，要么以 `assets/` 开头。

细则：

- **时间照抄官方**。官方写「10:00」就写 10:00，不要自己补成 10:00–11:00。
- **并行轨道写在 `会场`，不是 `形式`**。`形式` 说的是这一场是什么（演讲还是圆桌），
  `会场` 说的是在哪。两个分会场同时开，是两个 `会场`、两场都是 `演讲`。
- **字段值里不要出现裸 `|`**——它是讲者行的分隔符。（这一条取代了旧表格写法里
  「单元格里的竖线要转义成 `\|`」，表格已经不是日程的写法了。）
- 未公布的内容写 `- 状态:`，不留空、不编。
- **头像写 `assets/speakers/<slug>.webp`**，文件必须真在活动自带的资源目录里
  （`content/<slug>/assets/speakers/`），缺了构建会失败——线上就是一条 404。
  用 `npm run fetch:speakers` 从官方议程页抓（会统一转成 200px 的 WebP）。
- **摘要只放中文**。200 字以内的**直接摊在卡片上**（短摘要点开才看等于多一次点击）；
  更长的收进一个「摘要」的折叠块。官方中文议程里有原文就用原文，
  只有英文摘要就自己转述——页面不额外标注来源，读者看得出这是一段概述。
- **官方出处指向中文版**：多数官网认 `?lang=cn`（如
  `https://example.org/speakers/marco?lang=cn`），写的时候带上这个参数，
  读者点开就是中文页面。
- **讲者与机构的完整介绍写在讲者行的第 5 段**（见上面的五段说明）。
  构建器把它变成**日程卡片里讲者名后面的一个小图标**：点一下就展开那段介绍，
  **只在那个人第一次出现的地方**挂一个。
- **看这一场之前要知道的事（术语、注意事项、报名要求）写在 `- 备注:`**，
  可写多条；每条渲染成卡片上一个小图标，点开是全文。
  **不要为这些另开章节**——读者在场会门口扫的是这一场，不是页尾。
- **边会单独列一节**，不混在主议程里。
- 一组场次共用一个时段（官网常见的「Rapid Fire · 某某」）：每场各写一条，
  `形式` 写 `快闪`，别写成一条汇总行——时段分组由构建器按开始时间自动归并。

### 场次旁边的小注记

**某一场还没定下来的东西（主题待确认、讲者待定、时长可能有变），写在该场的
`- 状态:` 字段里，别收到页面末尾的「信息来源与待确认」里。**

理由很实在：读者在会场门口扫的是**这一场**，不是页面最后那节。等他翻到页尾才知道
这场的主题没定，已经来不及了。末尾那节是给「整份资料的可信度」用的，不是给单场
次打补丁的。

```markdown
#### 09:45–10:10 · 从模型到企业工作流：Agent 真正落地需要什么
- 形式: 演讲
- 会场: 主会场
- 状态: 主题待嘉宾确认
```

- **状态里有「待……确认 / 待……公布 / 待定」，构建器会自动把它升级成警示色**
  （「主题待嘉宾确认」也算，不要求三个字连写）。换成别的说法（「官方还没给」）就不亮了。
- 一场只有一个状态；多个待确认合并成一句（「主题与讲者均待确认」），别列一串。
- **官方标题整个是空的**（不是「待定」，是压根没给）——照写标题，
  把「讲题待公布」放进 `- 状态:`，不要自己编一个标题。
- 整场活动级别的待确认（「Day 2 分会场时间可能有变」）才放「信息来源与待确认」。
- 主持人不占讲者位：**写在讲者行的最后一段**（`姓名 \| 机构 \| 头像 \| 主持人`）。

## 机构与嘉宾的备注

**原则：机构与嘉宾的备注应该在它们最初出现的地方。**

读者站在会场门口扫的是**日程**，不是翻到页面末尾去对号入座。因此：
- **初次出现时就地标注**：写在讲者行的第 4 段（一句注记），机构的补充说明跟在机构名后面。
  - `- 讲者: Clemens Rawert | Langfuse by ClickHouse（LLM可观测性平台 · 金赞助） | assets/speakers/clemens-rawert.webp | 联合创始人`
  - 讲者行的五段是 `姓名 | 机构 | 头像 | 注记 | 完整介绍`，位置固定——
    **第三段是头像位**，写头像路径就得是 `assets/speakers/` 下真实存在的文件；
    没有头像就把第三段留空（`姓名 | 机构 | | 注记`），别把注记写进第三段。
- **后续场次不重复冗余说明**：同一个讲者或机构再次登台时，保持名称干净，不再堆叠相同注记。
- **不再单开「机构与嘉宾」一节**：讲者行里那一小段注记就地给全了；
  **履历、机构背景这类长了的信息写进讲者行第 5 段**，渲染成讲者名后面的小图标
  （点开是全文，只在那个人第一次出现处挂一个）。

每个实体注记保持精简（通常 5–25 字），直击要害：
1. **定位与赛道** —— 做什么的（大模型、向量数据库、具身机器人、端侧AI）。
2. **讲者角色** —— 负责什么（CEO、联创、首席架构师）。
3. **赞助与生态** —— 白金/金赞助、代表作。

**更长的介绍（简历、机构背景）写进讲者行第 5 段**，页面自动变成小图标：

```markdown
#### 10:10–10:25 · 构建Agent：昨天、今天与明天
- 形式: 演讲
- 会场: 主会场
- 讲者: Clemens Rawert | Langfuse by ClickHouse（LLM可观测性平台 · 金赞助） | assets/speakers/clemens-rawert.webp | 联合创始人 | Langfuse 联合创始人。Langfuse（现加入 ClickHouse）是全球最主流的开源 LLM 追踪、调试与评测平台之一。
```

## 前置知识（写进那一场的「备注」）

**判据只有一个：不懂这个词，这场分享是不是就听不懂？**

理解不了就别听——所以术语不是单开一节列在页尾，而是**挂到用得上的那一场**上，
写成那一场的 `- 备注:`，页面上是一个小图标，点开就是解释。

```markdown
#### 10:10–10:25 · 构建Agent：昨天、今天与明天
- 形式: 演讲
- 会场: 主会场
- 备注: 先搞懂 KV-Cache：大模型推理时缓存注意力键值的机制，直接影响首字延迟与并发成本。
```

- ❌「大模型：一种基于深度学习的人工智能模型。」——这是通识，浪费读者时间。
- ❌「Transformer：一种神经网络架构。」——除非这场分享就是讲 Transformer 的实现细节。

**一条备注对应一场**（可以写多条，但要挂在真的用得上的那一场上）。
术语解释比注记长是正常的——注记 5–25 字，备注可以是一段话。

## 行前清单

**每条是一个可执行动作**，不是状态。

- ❌「护照」——这是状态，不是动作。
- ✅「确认护照有效期 > 6 个月」。

**排序按紧迫度**，不按主题。距离开幕 ≤7 天时，报名截止 / 签证 / 票务核验必须在最前面。

用 Markdown 复选框：

```markdown
## 行前清单

- [ ] 在官网选好同声传译语言通道
- [ ] 报名「Agent 工程」分论坛（需单独审核）
- [ ] 预约展区 Demo 时段
- [ ] 准备名片和想问 Demo 团队的具体问题
```

构建器会把 `- [ ]` 变成**能真的打勾**的复选框，勾选状态存在当前浏览器本地（按活动分开存，**不跨设备同步**）。

## 社交与提问

读者在现场真正会做的事：去哪找人、怎么问问题、什么话题值得搭话。

写具体的：「展区 Demo 团队集中在展台右侧」「主论坛 Q&A 在每场结束后 3 分钟」「官方社区入口见官网」。
不写：「欢迎大家积极交流」。

---

## 信息来源与待确认

**每条来源：链接 + 检索日期。**

```markdown
## 信息来源与待确认

- 官网议程页：https://example.org/program （检索日期：2026-10-20）
- 官网票务页：https://example.org/tickets （检索日期：2026-10-20）

**待确认**：Day 2 分会场的具体开始时间可能调整，以现场公告为准。
```

**四种状态分清楚**：

| 状态 | 怎么写 |
| --- | --- |
| 已确认 | 直接当事实写在正文里，这里不用重复 |
| 未公布 | 「官方尚未公布具体时间」 |
