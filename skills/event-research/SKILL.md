# 活动调研：把一个活动变成一页能用的行程与准备

输入是一个活动名称或一条第三方票务链接，输出是一份 `event.md`——本站构建器直接读它。

**这个技能的价值不在「找到活动在哪」，而在「把碎片信息变成能决定去不去、排什么顺序、带什么去的东西」。**

**配套参考**（用到哪部分读哪部分，不必通读）：

- `references/verification.md` —— **查证手册**：怎么穿透第三方站、检索式清单、每类事实去哪确认、冲突怎么办。
  做阶段 1–3 和写「信息来源」之前读它。
- `references/writing-guide.md` —— **写作细则**：每一节该写什么、不该写什么，带正反例。
  动笔写 `event.md` 之前读它。

---

## 输入

| 项 | 要求 |
| --- | --- |
| 活动名称或链接 | **必需**，至少一项 |
| 参会角色 | 可选。知道就直接推荐；不知道就按活动的两类典型角色各给一套 |
| 关注方向 | 可选。用于排序「最重要的 3 件事」和选场建议 |
| 购票情况 | 可选。影响行前清单 |
| 出发城市 | 可选。影响交通与住宿建议 |
| 想解决的问题 | 可选。优先级最高 |

**日期基准**：以执行时可信的当前日期为准，活动日期按**活动所在地时区**理解。不确定就标注，不要假定。

**同名歧义**：存在多个同名活动且无法用日期、城市、主办方排除时，**先问用户**，不要挑一个就开始写。

---

## 阶段 1 · 特征提取与穿透（Probe & Fallback）

第三方票务站（活动行 / Luma / Eventbrite / Meetup）常有登录墙与反爬。
详见 `references/verification.md`。

1. 直接打开目标 URL。
2. **判断被挡**：403、登录弹窗、反爬验证、正文为空 —— 判定被挡后**最多再试一次**，不要循环重试。
3. 被挡时立刻提取特征值：
   - **纯数字 ID / slug**（例：`https://sh.huodongxing.com/event/1879040305100` → `1879040305100`）
   - **活动主体关键词**（例：`AI Engineer` `Shanghai` `2026`）
   - **平台名**（`huodongxing` / `luma` / `eventbrite`）
4. 用特征值进入阶段 2。

> 判定「读到了」的依据是**页面里确实有活动内容**，不是「返回了 200」。

---

## 阶段 2 · 定位官方信源（Canonical Discovery）

第三方页面是**二手**的。目标是找到主办方自己维护的**一手**信源。

**检索式组合**（逐个试，命中即停）：

```text
"<数字ID>" <平台名>            # 例："1879040305100" huodongxing
"<活动名>" <城市> <年份>        # 例："AI Engineer Shanghai 2026"
"<活动名>" program OR schedule OR agenda OR pdf
"<活动名>" 报名 OR 购票 OR 议程
site:<猜测的官方域名>
```

**锁定目标**：主办方独立主站（如 `ai.engineer/shanghai/2026`）、原生议程页（`/program`）、官方 PDF 议程、官方公告帖。

**信源分级**（写进「信息来源与待确认」时标注级别）：

| 级别 | 是什么 | 怎么用 |
| --- | --- | --- |
| A | 主办方官网 / 官方议程 / 官方 PDF / 官方票务页 | 可作为事实直接写 |
| B | 主办方官方社媒、演讲者本人确认 | 可写，但要注明是社媒口径 |
| C | 权威媒体、行业媒体 | 补充背景；与 A 冲突时以 A 为准并标出冲突 |
| D | 聚合站、转载、往年回顾 | 只作线索，不作事实 |

**冲突处理**：两个来源说法不一致 → 选级别高的写，并在「信息来源与待确认」里**并列写出两种说法**，不要私自抹平。

---

## 阶段 3 · 一手资料抓取与结构化（Primary Ingestion）

1. 打开官方议程页 / PDF 议程。
2. **多语言**：国际会议探测 `?lang=cn`、`/zh`、`/en` 等参数，对照中英文标题与讲者职务。
3. 逐场提取：
   - 精确到分钟的开始 / 结束时间（**不要自己推算**，页面写多少就写多少）
   - 场次类型：主会场 / 并行分会场 / 边会（Side Event）/ 工作坊
   - **是否需要单独报名**（很多分会场要单独审核，这条最容易漏）
   - 讲者姓名、所属机构、演讲标题、Abstract 原文
   - 会场 / 房间号
4. **保留专有名词与原题**，不要翻译成「大概的意思」。
5. 识别**并行冲突**：同一时段有多个场次 → 记下来，阶段 6 要用来给选场建议。
6. **一手素材能抓就抓，别手抄**：
   - `npm run fetch:speakers -- --event <slug> --source <议程页 URL>`
     把官方议程页上的讲者头像抓进 `content/<slug>/assets/speakers/`，统一转成 200px 的 WebP
     （热链的话官方改一次路径就是满屏 404）。
   - `node scripts/fetch-program.mjs <议程页 URL>` 把议程的一手字段抽成 `.work/program.json`
     （时间、轨道、形式线索、英文摘要、讲者与机构、头像、讲者页链接），照着它逐场填，
     不用手抄 60 遍。
   - 官方中文 PDF 只当**中文标题与姓名**的权威口径；**摘要往往只存在于英文页**，
     中文摘要要自己转述（页面上不标来源，短摘要直接摊开）。

---

## 阶段 4 · 实体背景补充（Entity Enrichment）

议程里出现的公司、开源项目、讲者，读者往往不认识。目标是**让读者能判断这场分享值不值得听**，不是写百科。

**每个实体最多 100 字，四要素**（有就写，没有就省）：

1. **定位与赛道** —— 这家公司/项目是做什么的，属于哪个方向。
2. **行业高度** —— 只写可核实的：公开融资、估值量级、标杆客户、GitHub 星数、论文/会议级别。**不写「业内领先」这种没有信息量的话。**
3. **讲者角色** —— 在团队里负责什么（创始团队 / 基础设施负责人 / 研究员）。
4. **演讲的技术深意** —— 这个题目对应生产环境里的什么工程问题。

**纪律**：
- 附可核实来源；找不到就**整段省略**，不写「据了解」。
- 推测的动机单独标成推测，不混进事实。
- 实体很多时，重点讲者写全，其余一句话带过。
- 生僻开源项目：搜 `"<项目名>" founder OR github OR architecture`，提炼 README 里的核心卖点。

---

## 阶段 5 · 前置知识萃取（Prerequisite Extraction）

从 Abstract **反推**「听懂这场分享必须先知道什么」，而不是罗列行业常识。

- **不单独成节**：每条术语挂到**真的用得上的那一场**上，写成那一场的 - 备注:。
- 一句话解释就够；指到具体场次是天然的（它就写在那一场里）。
- 只在「不懂就听不懂这场」时才写。业界人人皆知的（什么是 API、什么是容器）不要写。
- 不要凑数。宁可一条都没有。

---

## 阶段 6 · 交付（Action Matrix）

**紧迫度**：先算「距离开幕还有几天」。≤7 天的活动，行前清单里**必须**有报名截止、签证、票务核验这类有时限的事项，并且排在最前面。

### 「最重要的 3 件事」怎么选

按这个顺序取，**最多 3 条，不足不凑**：

1. **时限性** —— 有截止日期、需要提前办的事（单独报名、签证、早鸟票）。
2. **决策性** —— 会改变「去不去 / 听哪场」的关键信息（主论坛语言、有无同传、规模）。
3. **易错性** —— 大多数人会踩的坑（场地分散、需带什么、预约制）。

### 「推荐路线」

- **角色已知**：按该角色的关注点排，给出「必听 / 可听 / 可跳过」。
- **角色未知**：按该活动适用的**两类典型角色**分别给一套，并**指出并行冲突**（同一时段只能选一个）。
- 不要罗列全部日程——那是「日程」章节的活。

### 「行前清单」

- **紧急的在前**（按时间倒推，不是按主题分类）。
- 每条是一个可执行动作（动词开头），不是状态（「带好护照」不是，「确认护照有效期 > 6 个月」是）。
- 用 Markdown 复选框 `- [ ]`，构建器会把它变成能打勾的清单。

## 输出格式

**只输出 `event.md` 的内容**，不附聊天式说明、不加前后缀。

> 每一节的具体写法、正反例见 `references/writing-guide.md`。下面的骨架只给结构，不给写法。

### front matter

```yaml
title: 活动名称            # 必填
summary: 一句话简介         # 一句话说清「什么活动 + 适合谁」
start: 2026-11-05          # YYYY-MM-DD，未知就省略
end: 2026-11-06            # 省略时按单日活动处理
timezone: Asia/Shanghai    # IANA 名，已知就写
city: 城市
venue: 会场
venue_url: https://...     # 会场的官方页面（酒店/场馆官网），知道就写
address: 地址
organizer: 主办方
website: https://...
agenda_url: https://...
ticket_url: https://...
map_url: https://...
tags: [标签, 标签]
```

- **只保留已知字段**；未知字段整行省略（不要写 `未知`、不要留空值、不要写示例地址）。
- 日期必须是 `YYYY-MM-DD`；时区必须是 IANA 名；链接必须是真的 HTTP(S) 地址。
- 活动跨越多天时 `start` 与 `end` 都要写。
- **`venue` 与 `venue_url` 一起写**：页面上场地名会变成链接，头部还有「场地」按钮
  （手机上头部信息是收起来的，靠它才点得到）。只给 `map_url` 不够——
  地图回答「怎么过去」，`venue_url` 回答「这到底是哪一家」。
  ⚠️ 同名的场所有好几家时，地图的搜索词会落到别的那家去；
  名字用官方中文名，地图查询带上地址。

### 正文

顺序固定，无内容的章节省略：

1. 引用块：**最重要的 3 件事**（正文第一段）
2. `## 速览`
3. `## 日程`（一天一个 `###`，一场一个 `#### 时间 · 标题` + 显式字段；讲者与机构的介绍、术语、注意事项都写在那一场内）
4. `## 推荐路线`（放在日程之后——读者已经看过日程，再看怎么选）
5. `## 行前清单`
6. `## 社交与提问`
7. `## 信息来源与待确认`

**写法约定**：

- 主要章节用二级标题（`##`），章节内部可用三级标题（`###`）。
- **没有「机构与嘉宾」「前置知识」这两节**：它们的内容都变成日程里的图标提示。
- **机构与嘉宾的备注直接写在最初出现的地方**：写在那一场的**讲者行第 4 段**
  （职位、赛道、赞助级别），后续场次不重复说明。
- **讲者的完整介绍写讲者行第 5 段**：页面渲染成讲者名后面的小图标（点开是全文）。
- **看这场之前要知道的事写 `- 备注:`**：术语、注意事项、报名要求，可写多条，
  每条渲染成卡片上的小图标。不要为这些另开章节。
- 字段值里不要出现裸 `|`（它是讲者行的分隔符）。
- 折叠块用 `<details markdown="1">` + `<summary>`，**标签和 Markdown 内容之间留空行**。
- 不写脚本、不写危险链接。

### 日程的写法

**日程不是表格**：一天一个 `###`，一场一个 `#### 时间 · 标题`，下面跟字段列表。
构建器把这一整节接管，渲染成自适应卡片（一场一张，占满整行）。

```markdown
## 日程

### Day 1 · 11 月 5 日（周四）主题一句话

#### 09:30–09:45 · 开场与年度趋势
- 形式: 开场
- 会场: A 馆主论坛
- 讲者: 主办方团队 | AI Engineer
```

字段是**封闭集合**，拼错构建就报错并给行号：
`形式`（`演讲`/`圆桌`/`快闪`/`开场`/`闭幕`/`茶歇`/`边会`/`行程`/`签到`）、`会场`、
`讲者`、`时长`、`状态`、`看点`、`摘要`、`备注`、`出处`。详见写作细则。

- **每天的第一场决定活动的开始时刻**——页面上的倒计时指向它，而不是当天 00:00。
  有签到就把签到写成第一场（`形式: 签到`，**不写 `会场`**，它发生在入口），
  读者看到的「还有 3 小时」才指向真正要到的时刻。
  没有签到信息就别编——第一场是演讲就写演讲。
  ```
  #### 08:30–09:30 · 签到
  - 形式: 签到
  - 备注: 签到地点与入场证件要求以主办方通知为准。
  ```
  ⚠️ 签到时刻**要有出处**：官方议程页没写签到的，就在 `- 备注:` 里说明
  「官方页面未列出，以主办方通知为准」——别把没核实的东西写成板上钉钉的事实。

- **并行轨道写在 `会场`，不是 `形式`**——`形式` 说的是这一场是什么（演讲还是圆桌），
  `会场` 说的是在哪。两个分会场同时开，是两个 `会场`、两场都是 `演讲`。
- 需要单独报名的场次，在 `看点` 里写明。
- 边会单独列，不混在主议程里。
- **单场次还没定下来的东西**（时间待公布、主题待确认、讲者待定），
  写进**该场的 `- 状态:` 字段**：
  ```
  #### 10:30–11:15 · 工程实践
  - 形式: 演讲
  - 会场: 主会场
  - 状态: 讲者待确认
  ```
  渲染成一张警示色的小标签。**不要收到页面末尾的「信息来源与待确认」里**——
  读者在会场门口扫的是这一场，等翻到页尾才知道就晚了。
  整场活动级别的待确认（「Day 2 分会场时间可能有变」）才放「信息来源与待确认」。
- **讲者行五段固定**：`姓名 | 机构 | 头像 | 注记 | 完整介绍`，后四段可省。
  第三段是**头像位**（`assets/speakers/<slug>.webp`，文件必须真实存在，缺了构建会失败）；
  第五段是**完整介绍**（渲染成讲者名后面的小图标，点开是全文，只在第一次出现处挂）。
  没有头像就把第三段留空，别把注记写进第三段。
- **摘要只放中文**：200 字以内直接摊在卡片上，更长的收进「摘要」折叠块。
  官方中文议程里有原文就用原文，只有英文摘要就自己转述——不用额外标来源。
- **看这场之前要知道的事（术语、注意事项）写 `- 备注:`**：可写多条，每条渲染成
  卡片上的小图标。**不要为这些另开章节**——读者在场会门口扫的是这一场。
- **官方出处指向中文版**：链接带上 `?lang=cn`（多数官网认这个参数）。
- **「会场」按官方给的场地写**，别按标题文字猜——同一场活动的中文版标题和英文版
  常常对不上，按文字匹配会把整个分会场误标成主会场。

### 「信息来源与待确认」

- 每条来源写**链接 + 检索日期**。
- 关键事实（时间、地点、票务、嘉宾、场次）在**正文对应位置附近**也留一个可追溯来源，不要只集中在最后一节。
- 分开写清楚四种状态：
  - **已确认** —— 来源级别 A/B，事实。
  - **未公布** —— 官方还没出。
  - **来源冲突** —— 两种说法并列。
  - **推测** —— 明确标成推测，写清推测依据。

## 边界情况

| 情况 | 表现 | 怎么办 |
| --- | --- | --- |
| 反爬 / 登录墙 | 403、弹登录框 | 提数字 ID + 关键词反查官方站；最多再试一次 |
| 议程 TBA | 页面写「待公布」 | **就在那一场的 `- 状态:` 字段写 `讲题待公布`**，不要留空、不要编 |
| 多轨并行冲突 | 同一时段多场 | 在「日程」里标出，并在「推荐路线」里明确指出只能选一个 |
| 生僻新项目 | 搜不到什么 | 搜 GitHub / 官网，把 README 卖点写清；找不到就省略这段 |
| 多个同名活动 | 无法区分 | **先问用户**，不要挑一个开写 |
| 来源冲突 | 两个说法不一样 | 高级别优先，并列写出两种说法 |
| 官方没给时区 | 无时区信息 | 用活动所在地合理推断并**写进 `timezone`**；实在推断不出就省略该字段（构建器会按 UTC 计算并提示） |

---

## 反编造红线

以下每一条都要守住：

- **不编造**机构、讲者、票价、时间、地点、报名状态、语言、同传安排。
- 推测**单独标注**，不与事实混排。
- **往届资料不写成今年已确定的安排**。
- 检索日期必写。
- 「最重要的 3 件事」不足 3 条就不写满 3 条。
- 前置知识不堆通识，也不另开章节——挂到用得上的那一场上。
- 拿不到可靠信息时，**说明限制并问必要的问题**，不要用一份看起来完整的文档掩盖缺口。
